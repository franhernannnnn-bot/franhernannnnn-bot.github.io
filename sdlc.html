Ciclo de vida del desarrollo de software (SDLC)

Aplicación de un proceso completo de desarrollo al sitio web Zacahuil Huasteco, desde la planeación de requisitos hasta el despliegue, monitoreo y mejora continua. La propuesta se organiza con Scrum e incorpora seguridad temprana, automatización y retroalimentación.

01 · Ciclo de vida

Etapas del SDLC aplicadas al sitio web

Etapa 1

Planificación y análisis

Identificar usuarios, objetivos y requisitos: consultar el catálogo de zacahuil, ver promociones, agregar productos al carrito y contactar al negocio.

Etapa 2

Diseño

Definir navegación, estructura HTML, estilos CSS, comportamiento JavaScript, diseño adaptable y accesibilidad básica.

Etapa 3

Desarrollo

Construir las páginas Inicio, Tradición, Productos, Promociones, Galería, Contacto y la documentación SDLC.

Etapa 4

Pruebas y seguridad

Probar enlaces, buscador, carrito, formularios y vista móvil; revisar entradas, dependencias y posibles errores antes de publicar.

Etapa 5

Despliegue

Publicar una versión revisada en el servidor de pruebas o alojamiento web. Guardar una copia de seguridad antes de actualizar.

Etapa 6

Operación y mejora

Revisar fallos, rendimiento, visitas y comentarios. Priorizar mejoras para el siguiente Sprint.

Alcance real de esta práctica: esta página documenta el proceso y ofrece un checklist de revisión. La automatización CI/CD, Docker y las herramientas de monitoreo descritas más adelante son una propuesta de implementación; no se activan por agregar esta página al sitio.

02 · Gestión ágil

Metodología ágil y Scrum

La metodología ágil permite entregar mejoras pequeñas, recibir comentarios y adaptar los requisitos. Scrum organiza el trabajo mediante un Product Backlog priorizado, Sprints de duración fija, reuniones breves y revisión del incremento con el usuario.

Roles sugeridos

  • Product Owner: representa las necesidades del cliente y prioriza el catálogo, promociones y pedidos.
  • Scrum Master: facilita el proceso y ayuda a resolver impedimentos.
  • Equipo de desarrollo: diseña, programa, prueba y documenta la solución.

Eventos Scrum

  • Planificación del Sprint: definir el objetivo y las tareas.
  • Seguimiento diario: revisar avances y bloqueos.
  • Revisión: demostrar el incremento al usuario.
  • Retrospectiva: acordar cómo mejorar el proceso.

03 · Seguridad temprana

Shift Left: seguridad desde el inicio

Shift Left significa incorporar controles de seguridad desde la planificación y el desarrollo, en lugar de esperar hasta el final.

Durante el diseño

Definir qué datos se recopilan, minimizar datos personales y establecer permisos adecuados si se agrega un panel administrativo.

Durante el desarrollo

Validar entradas, evitar insertar contenido no confiable como HTML, no guardar contraseñas o claves en el código y usar HTTPS en producción.

Antes de publicar

Revisar dependencias, formularios, permisos de archivos, enlaces externos y mensajes de error. Corregir primero los riesgos críticos.

04 · Automatización

Propuesta de CI/CD

La integración continua (CI) verifica cada cambio; la entrega o despliegue continuo (CD) prepara y, si se autoriza, publica una versión validada.

1. Código

Guardar cambios en Git con mensajes claros y ramas para nuevas funciones.

2. Validación automática

Ejecutar revisión de formato, comprobación de enlaces, pruebas disponibles y análisis de dependencias.

3. Construcción

Preparar los archivos del sitio y generar un artefacto versionado.

4. Entorno de pruebas

Publicar primero en staging y realizar pruebas funcionales y de seguridad.

5. Aprobación y despliegue

Solicitar aprobación, publicar la versión y conservar un procedimiento de reversión.

Herramientas posibles: Git y GitHub para control de versiones; GitHub Actions para automatizar verificaciones; un servidor de pruebas para validar antes de producción. Para este sitio estático, los pasos deben configurarse en el repositorio: no se ejecutan automáticamente todavía.

05 · Contenedorización

Uso de Docker

Docker puede empaquetar el servidor web y los archivos de la aplicación en una imagen reproducible, reduciendo diferencias entre el equipo de desarrollo y el servidor. Para una web HTML/CSS/JavaScript estática, se puede usar un contenedor Nginx sencillo.

Flujo propuesto

  1. Guardar los archivos del sitio en un repositorio.
  2. Crear un archivo Dockerfile con Nginx y copiar los archivos web a su directorio público.
  3. Construir la imagen y ejecutar el contenedor en desarrollo.
  4. Probar navegación, recursos CSS/JS y diseño adaptable.
  5. Etiquetar la versión y desplegarla solo después de las verificaciones.

Nota: Docker es una propuesta para la práctica; no es requisito para abrir el sitio localmente con XAMPP o directamente en el navegador.

06 · Observabilidad y feedback

Monitoreo y mejora continua

Registros (logs)

Registrar errores del servidor y fallos reportados, sin incluir contraseñas ni información sensible.

Métricas

Observar disponibilidad, tiempo de carga, errores y páginas más consultadas. Utilizar PageSpeed Insights para evaluar rendimiento.

Experiencia del usuario

Recopilar comentarios sobre el catálogo, la navegación y el proceso de pedido; usar analítica solo con la configuración y avisos de privacidad apropiados.
